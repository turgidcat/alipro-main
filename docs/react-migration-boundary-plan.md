# React 迁移边界方案

> 最后更新：2026-06-09
> 适用项目：`alipro-main`
> 目标：避免在前端迁移过程中继续制造新的历史包袱，尤其避免再次掉进“vibe coding 式半迁不迁”的混乱状态

---

## 1. 为什么要先写这份文档

你现在这个项目已经有两个现实：

1. 当前前端不是 React 工程，而是静态 `HTML + CSS + JS`
2. 当前前端确实已经开始出现越来越多的结构性问题

所以“要不要迁 React”这个问题，其实答案已经不是重点了。

真正重点是：

`怎么迁，才不会比现在更乱`

这份文档就是专门干这个的。

---

## 2. 先说结论

### 2.1 我支持迁 React

从长期看，这个项目应该迁。

原因很直接：

- 当前前端全局函数过多
- 页面状态散落在 DOM、全局变量和多个脚本文件里
- 一个小改动容易影响一大片
- 缓存、脚本顺序、全局覆盖问题会反复出现

### 2.2 但我不支持“整站一把梭”

因为你现在还有三个更核心的东西在变：

- 创作主链逻辑还在调整
- 数据结构还在重构
- 首页与资料库职责还在收口

这个时候整站立刻重写成 React，很容易出现：

- 旧逻辑没理顺
- 新架构又开工
- 最后既有业务风险，也有框架迁移风险

### 2.3 只能走“有边界的渐进迁移”

但这里有个前提：

`渐进迁移不是今天改一个弹窗、明天改一个按钮`

真正安全的渐进迁移，必须按：

`完整业务区域`

来切。

---

## 3. 什么样的迁移方式最危险

这一节非常重要，因为它基本就是“以后禁止做什么”。

## 3.1 最危险的方式：按零件碎片迁

比如：

- 先把一个按钮改 React
- 再把一个弹窗改 React
- 再把一个卡片改 React
- 其他区域继续靠原生 JS 控

这种迁法短期看很灵活，长期看最容易出怪物。

为什么危险：

- 一个功能跨两套渲染体系
- 数据流会分裂
- DOM 控制权会互相覆盖
- bug 会变得很难定位

说白了，这种迁法最后很容易变成：

`半个页面像 React，半个页面像 2018 年的原生脚本拼接站`

## 3.2 第二危险的方式：边改框架边改业务主链

比如一边迁 React，一边同时：

- 改创作流程
- 改章节逻辑
- 改数据结构
- 改按钮布局

这会导致：

- 出问题时，不知道是业务逻辑错了
- 还是接口变了
- 还是 React 组件状态错了
- 还是旧脚本还在接管一部分 DOM

这种情况最适合制造“谁都觉得自己改得没问题，但项目整体越来越怪”的氛围。

## 3.3 最危险的心理陷阱：觉得先搭着能跑就行

这就是典型的 `vibe coding` 风险区。

在这种心态下，最容易出现：

- 新旧接口双套并存但没人清理
- 旧脚本没删，新组件又上了
- 一个状态存 3 份
- 页面看似还能用，但后面越修越脆

所以这里必须明确：

`迁移阶段禁止“先搭着跑，以后再整理”这种想法`

---

## 4. 什么样的迁移方式是安全的

## 4.1 按“业务岛”迁，不按“组件碎片”迁

正确方式不是：

`先迁一个按钮`

而是：

`先迁一个完整业务区域`

什么叫完整业务区域：

- 它有明确边界
- 它有相对独立的数据输入输出
- 它可以在新旧系统之间短暂共存

例如：

- 首页创作主链
- 资料库
- 更新日志/引导页

这几个都算完整业务区。

## 4.2 新旧前端必须物理隔离

这条是铁律。

React 迁移阶段，必须做到：

- React 只接管自己的挂载根节点
- 原生 JS 不再去操作 React 挂载区域内部 DOM
- React 组件也不要反向直接改旧页面散落的 DOM

一句话：

`谁的地盘谁做主`

不能出现：

- React 渲染一个卡片
- 原生脚本再去 `document.getElementById` 改它里面的内容

这种写法后面一定炸。

## 4.3 数据层优先统一，视图层再迁

这也是铁律。

迁 React 之前，必须先问：

`这个区域的数据来源是不是已经基本稳定`

如果数据源还在乱：

- 一会读 `chapters.outline`
- 一会读 `chapter_plans`
- 一会又从前端临时状态拼

那这时候迁 React 只是把“乱”组件化，不是把“乱”解决掉。

所以迁移顺序必须是：

1. 先定主数据源
2. 再定接口
3. 再迁视图层

---

## 5. 当前项目里，哪些区域能迁，哪些不能碰

这一节是最关键的边界表。

## 5.1 可以优先迁的区域

### A. 首页创作主链容器

也就是你现在最核心的 3 步：

- 全书规划
- 单章设置
- 正文生成

为什么它适合优先迁：

- 这是当前最重要的业务区
- 你后续会长期迭代它
- 现在它的交互复杂度已经明显超出原生脚本舒适区

但注意：

不是先迁其中一个按钮，而是把“首页创作主链”作为一个完整 React 子应用来接管。

### B. 资料库页面

资料库适合第二批迁。

原因：

- 它和首页职责已经逐步分离
- 数据展示明显比即时创作交互更稳定
- 很适合用 React 做列表、筛选、详情结构

### C. 外观设置这类强交互弹窗

这类弹窗适合作为 React 子模块练手，但前提是：

- 它必须单独挂载
- 不和首页主链数据纠缠

所以它可以迁，但不应该优先于首页主链。

## 5.2 暂时不要迁的区域

### A. 底层生成链仍在剧烈变化的部分

例如：

- 章节目标与细纲结构
- 剧情线到单章的映射
- 推进反馈闭环

这些逻辑现在还没完全定型。

如果边迁框架边改这一层，非常容易把问题搅在一起。

### B. 仍严重依赖旧全局脚本联动的局部弹窗

如果某个弹窗本身还在依赖：

- `window.xxx`
- 多个全局变量
- 直接改多个页面 DOM

那它不适合独立先迁。

除非先把它的数据和控制权拆出来。

### C. 纯展示辅助页

例如：

- 更新日志
- 启动说明

这些页面迁 React 的收益最低，优先级应该放后。

---

## 6. 推荐迁移顺序

## 6.1 第一阶段：不先迁 React，先把创作主链数据源坐稳

目标：

- 完成 `chapter_plans` 收口
- 明确 `book_plans / volume_plans` 方向
- 明确剧情线与章节目标的关系

这一阶段 React 不必急着上。

因为这一步是在给未来的 React 组件准备稳定数据土壤。

## 6.2 第二阶段：把首页创作主链作为独立 React 子应用迁入

这一步才是 React 真正开始的起点。

目标：

- React 只接管首页主创作区域
- 旧导航、旧其他页面先不动
- React 区域通过 API 读写稳定数据

这一步不是“改全站”，而是：

`先做一个被边界包起来的新首页工作台`

## 6.3 第三阶段：资料库迁入 React

原因：

- 等首页创作链稳定后，再迁资料库
- 这时共享数据模型会更清楚

## 6.4 第四阶段：清理旧脚本与重复结构

最后才做：

- 删除已废弃全局脚本
- 删除重复 DOM
- 删除过渡期桥接逻辑

注意顺序不能反。

不是先删再说，而是：

`新区域稳定后，再拆旧区域`

---

## 7. 技术边界规则

这部分可以视为以后实施时的“纪律”。

## 7.1 一块区域只允许一个视图主控

例如首页创作台：

- 如果 React 接管
- 原生 JS 就不能再继续直接操作其内部 DOM

## 7.2 新组件不准直接依赖旧 DOM 查询

禁止这种写法：

```js
document.getElementById('outline').value
```

出现在 React 组件内部逻辑里。

因为这等于把旧系统的脐带继续插在新组件上。

## 7.3 状态只允许有一个正式来源

例如当前章规划：

正式来源应该是：

- API 返回的 `chapter_plans`

而不是：

- 一份在 React state
- 一份在全局变量
- 一份在 localStorage
- 一份在隐藏 DOM

## 7.4 迁移期必须允许桥接，但桥接层要短命

桥接层可以存在，比如：

- React 调旧接口
- 旧页面临时嵌 React 容器

但桥接层必须满足：

- 有明确用途
- 有明确退出时间
- 不允许变成永久层

---

## 8. 最适合你的迁移方案

结合你现在项目状态，我给的最现实方案是：

## 8.1 不是整站 React 重写

因为现在这样做风险太高。

## 8.2 也不是继续长期死守原生脚本

因为当前复杂度已经开始超出它的舒适区。

## 8.3 而是“三段式”

### 第一段：先稳定底层主链

也就是现在我们正在做的事。

### 第二段：首页创作台整块迁 React

不是迁零件，是整块迁。

### 第三段：资料库整块迁 React

这样就能做到：

- 不会同时重写一切
- 也不会继续任由旧结构无限膨胀

---

## 9. 最终建议

对你这个项目来说，最危险的不是“渐进迁移”这四个字。

最危险的是：

`没有边界的渐进迁移`

所以后面如果要迁 React，必须遵守这条总规则：

`按业务区域整块迁，不按局部零件零碎迁`

我给你的建议顺序很明确：

1. 继续把创作主链底层收口
2. 等这一层稳定后，把首页创作台整块迁成 React 子应用
3. 再迁资料库
4. 最后清旧脚本

如果不按这个顺序来，确实很容易在 `vibe coding` 下越迁越乱。

如果按这个顺序来，React 迁移反而会成为一次“收口”和“减债”，而不是新增一层债。
