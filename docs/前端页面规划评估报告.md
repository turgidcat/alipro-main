| 维度 | 评分 (1-5) | 说明 |
|------|-----------|------|
| **路由结构** | 2 | 路由配置存在但形同虚设，核心页面（BooksPage）内部自行 sniff URL，绕过 React Router |

## 二、逐项分析

### 2.1 路由结构 — 路由配置是"剧场"

**现状：**

`router.jsx` 定义了 10 条路由，但实际行为是：

```
/books          → BooksPage (component checks: am I list? am I detail?)
/books/outlines → BooksPage (component checks: am I outlines?)
/books/characters → BooksPage (component checks: am I characters?)
/books/storylines → StorylineManagementPage (另一个组件)
/books/chapters → BooksPage (component checks: am I chapters?)
```

BooksPage **不用 `useLocation()`、不用 `useParams()`、不用 `<Link>`**，而是在每次 render 时直接读 `window.location.pathname`，然后内部 if-else 切换视图。子页面之间的导航用的是 `window.location.href`，触发**整页硬刷新**。

**问题：**
- React Router 配了 5 条路由指向同一个组件，但这个组件完全不理会 Router，自己嗅 URL。等于 Router 白配了。
- 用户在 `/books` 和 `/books/outlines` 之间切换时，整个 React 应用销毁重建，所有状态丢失，重新请求 API。
- 如果将来加 base path（如 `/app/books`）或做 SSR，这种写法会直接炸。

**应该怎么做：**

```
方案 A（推荐，小改）：让 BooksPage 内部用 useLocation() + <Link>，消除硬刷新
方案 B（推荐，中改）：每个子页面拆成独立组件，各路由各组件，彻底消除 pathname sniffing
```

### 2.2 BooksPage — 2600 行 God Component

**这是当前前端最大的结构性债务。**

一个文件管理了 **8 个视图**、**57 个 useState**、**18 个独立 API 调用**、**322 行内联 CSS**、一个 canvas 图片裁剪器。

| 子系统 | 行数 | 应该是 |
|--------|------|--------|
| 书籍列表 + 过滤 + 批量操作 | ~220 行 | `BooksListPage.jsx` |
| 书籍详情概览 | ~110 行 | `BooksSummaryPage.jsx` 或 `BookDetailLayout.jsx` |
| 大纲编辑 + 卷计划 CRUD + AI 生成 | ~220 行 | `BooksOutlinePage.jsx` |
| 角色管理 CRUD + AI 批量生成 + 头像裁剪 | ~300 行 | `BooksCharacterPage.jsx` |
| 章节列表（只读） | ~75 行 | `BooksChapterPage.jsx` |
| 剧情线（只读） | ~78 行 | 已有独立页面，应合并 |
| 创建/编辑书弹窗 | ~80 行 | `BookEditorModal.jsx` |
| 头像裁剪弹窗 | ~50 行 | `AvatarCropModal.jsx`（通用组件） |
| 内联 CSS | 322 行 | `books-page.css` |
| 工具函数 + 常量 | 325 行 | `lib/booksUtils.js` + `config/genres.js` |

**附加问题：**
- `requestJson` 自建了一个请求工具，和 `workbenchApi.js` 里的 `request()` 功能完全重复。如果将来改鉴权逻辑（比如加 token refresh），要改两处。
- `genreCategoryMap`（16 个分类 50 个子分类）写在组件内部，workbench 那边的 `deepseek.js` 和 `constants.js` 也各有一份类似的 genre 映射。应该收敛到一处。
- 新建角色表单和编辑角色表单的 JSX 几乎一模一样但写了两遍（约各 150 行）。

**建议拆分方案：**

```
pages/books/
  BooksListPage.jsx         — 列表 + 搜索过滤 + 批量删除
  BookDetailPage.jsx        — 详情概览 + 子导航
  BookOutlinePage.jsx       — 大纲 + 卷计划
  BookCharacterPage.jsx     — 角色 CRUD
  BookChapterPage.jsx       — 章节列表
  BookStorylinePage.jsx     — 剧情线（合并现有独立页面）

pages/books/components/
  BookCard.jsx              — 书籍卡片
  BookEditorModal.jsx       — 创建/编辑书
  AvatarCropModal.jsx       — 头像裁剪（通用）
  CharacterForm.jsx         — 角色（新建 + 编辑共用）
  CharacterCard.jsx         — 角色卡片
  VolumePlanCard.jsx        — 卷计划卡片
  BookDetailLayout.jsx      — 通用详情页布局（侧栏导航 + 内容区）
```

### 2.3 状态管理 — prop drilling 深渊

**现状：**

App.jsx 是整个 workbench 的"状态中转站"。它从 7 个 hook 中拿到约 **90-100 个独立状态值 + setter**，打包成 3 个 prop bundle（`chapterConfigProps` 22 个、`contentWorkspaceProps` 20 个、`revisionProps` 24 个）+ 8 个直接传给 GlobalBar 的 prop + 32 个直接传给 WorkbenchOverlays 的 prop。

```
useWorkbench() ──── 60 个值 ───┐
useChapterWorkbenchViewModel() ── 15 个值 ───┤
useWorkbenchEditors() ──── 9 个值 ───┤
useRevisionNavigator() ──── 12 个值 ───┤  → App.jsx → 子组件
useDrawerMemory() ──── 4 个值 ───┤
useWorkbenchActions() ──── 40 个入参 + 12 个返回 ───┤
useWorkbenchShortcuts() ──── 12 个值 ───┘
```

`WorkbenchOverlays` 一个人就吃 32 个 prop，全展开的话函数签名有半屏幕长。

**现在能跑不代表一直能跑。** 每加一个新功能（比如流式生成），就要往这条链里塞新的 state + setter + callback，修改链条上的每一个中间层。

**建议：** 不需要上 Redux（太重），也不需要 Zustand（过早引入依赖），但应该用 React Context 做分层隔离：

```
Context 层级：
  WorkbenchContext    — 核心状态（chapterNumber, draftChapterPlan, isGenerating 等）
  ChapterContext      — 章节配置相关（planningState, chapterContext, storylineOptions）
  GenerationContext   — 生成相关（generationState, readiness, riskReview）
  RevisionContext     — 校改相关（revisionDraft, suggestions, error）

好处：
  1. WorkbenchOverlays 不再需要 32 个 prop，useContext(GenerationContext) 就够了
  2. 新增功能（流式生成）只需要在对应 Context 里加字段
  3. 子组件可以直接 useContext 而不需要层层传递
  4. 现有的 hooks 结构基本不变，只是返回值挂到 Context 而不是 prop
```

### 2.4 样式体系 — 三套并存

**当前有三套样式方案并行运作：**

| 方案 | 使用者 | 问题 |
|------|--------|------|
| **Tailwind CSS v4**（空壳配置） | AppLayout、WorkbenchStage、部分新版组件 | tailwind.config.js 的 extend 为空，所有设计 token 都在 CSS variables 里，Tailwind 只充当 layout 工具 |
| **app-shell.css**（3071 行） | 大部分组件 | 包含 modal、revision、form、button、generation 等全部样式，混杂 800 行废弃类 |
| **内联 `<style>` JSX** | BooksPage（322 行）、GenerationLogicPage（800 行） | 全局污染，不可 tree-shake，无作用域隔离 |

**具体问题：**

1. **Tailwind 配置为空，token 不入 Tailwind。** `styles.css` 定义了 70+ 个 CSS 变量（`--panel-surface`, `--text-muted`, `--radius-panel` 等），但 Tailwind 不知道它们。所有组件用 `bg-[color:var(--panel-surface)]` 这种 arbitrary value 语法去消费。这不比直接写 CSS 类好多少。

2. **app-shell.css 是历史遗留大杂烩。** 3071 行，涵盖 modal 系统、revision diff 视图、表单控件、书籍规划卡片、generation 面板……混合了三代 UI 的样式。其中 `.app-navbar`、`.nav-link`、`.nav-brand` 等导航样式已被 AppLayout.jsx 的 Tailwind 写法取代，但 CSS 类还留着。

3. **两套按钮体系共存。** `styles.css` 定义了 `--btn-*` token，`app-shell.css` 定义了 `.solid-btn` / `.ghost-btn` / `.nav-btn` / `.action-btn` / `.danger-solid-btn` 五个类，新版组件可能用 Tailwind 自行组合。三种方式做同一件事。

**建议：**

```
短期（P3 阶段末尾）：
  1. 把 Tailwind extend 配起来，把 styles.css 里的 token 注册为 Tailwind theme
     → bg-panel-surface 代替 bg-[color:var(--panel-surface)]
  2. 把 app-shell.css 拆分为语义化文件：
     workbench-layout.css（已有）
     modal.css
     revision.css
     form-controls.css
     generation-panel.css
  3. BooksPage / GenerationLogicPage 的内联 style 提取为独立 CSS 文件

中期（P4）：
  4. 选定一套按钮/表单方案，废弃其他
  5. 消除 arbitrary value 语法
```

### 2.7 Workbench 区域 — 相对健康

**做得好的地方：**

1. **组件拆分粒度合理。** GlobalBar / ChapterConfigPanel / ContentWorkspace 三大块 + 6 个 Modal + 4 个 Drawer + 4 个通用组件，职责清晰。
2. **hooks 分层有意义。** useWorkbench（状态）→ useChapterWorkbenchViewModel（派生值）→ useWorkbenchEditors（编辑操作）→ useWorkbenchActions（异步操作），层次分明。
3. **lib/ 抽象质量不错。** chapterPlan.js (445 行)、revisionDiff.js (264 行)、generationActions.js (136 行) 等都是纯逻辑，无 UI 依赖，可测试。
4. **workbenchApi.js 集中管理 API 调用**（1165 行），除了 BooksPage 的 requestJson 之外没有散落的 API 调用。

**可改进：**

1. **ContentWorkspace.jsx 只有 132 行，但它应该是"正文编辑器 + 流式输出"的核心区域。** 随着流式生成的加入，这个组件会急剧膨胀。建议现在就拆分为 `ContentWorkspace.jsx`（容器）+ `GenerationControlPanel.jsx`（生成按钮 + readiness + risk review）+ `StreamingTextView.jsx`（流式文本渲染）+ `ChapterContentView.jsx`（已持久化的正文展示）。
2. **PanelCard.jsx 的 flat/card 变体** — 目前只有 workbench 内用，但如果 BooksPage 拆分后也会用到，应该提升为 `components/PanelCard.jsx`。

## 三、优先级排序

如果要从最紧急的开始治理，我建议这个顺序：

| 优先级 | 改动 | 理由 |
|--------|------|------|
| **P0** | BooksPage 拆分 | 2600 行 God Component 是最大的维护障碍。每次改 Books 相关功能都要在一堆 if-else 里找代码。拆分后每个文件 200-400 行，新人上手快十倍 |
| **P1** | 引入 React Context（至少 GenerationContext + RevisionContext） | 90+ 个 prop 的 drilling 链条已经很难维护。流式生成会加 5-8 个新状态，不改 Context 的话链条会断 |
| **P1** | 消除 `window.location.href` 硬刷新 | BooksPage 子页面之间的导航改为 `<Link>` / `useNavigate()`，用户体验和性能立刻提升 |
| **P2** | 清理死代码（genre-ui + 3 展示页 + styleTheme.js） | ~3000 行无用代码增加认知负担和构建体积 |
| **P2** | 合并 requestJson 到 workbenchApi.js | 消除鉴权逻辑的重复维护 |
| **P3** | 样式体系统一（Tailwind token 化 + CSS 文件拆分） | 不影响功能，但影响长期开发效率 |
| **P3** | genre 常量收敛 | 三处独立维护 genre/subgenre 映射，早晚会分叉 |

## 五、与流式生成改造的关系

流式生成改造本身（`docs/流式生成改造执行方案.md`）不需要先做以上重构。两者的依赖关系：

- **Phase 1-2（后端）：** 完全独立，不涉及前端
- **Phase 3（前端 API 层）：** 独立，只加一个函数
- **Phase 4-5（前端 Action + 状态）：** 需要在 useWorkbench.js 加 `streamingText`、`batchProgress` 等新状态。在现有 prop drilling 架构下可以工作，但会让 App.jsx 的 prop 链条更长
- **Phase 6（前端 UI）：** ContentWorkspace.jsx 需要大量改动（流式渲染 + 批量进度条），如果现在不拆分，改造后可能达到 300+ 行

**建议：** 流式生成和 BooksPage 拆分可以并行。Context 化可以稍后做，但 Phase 6 之前最好至少把 ContentWorkspace 拆一下。
