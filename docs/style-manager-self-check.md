# Style Manager 自检机制

> 适用页面：`/style-manager`
> 目标：先挡住会影响用户判断的布局 bug，再做审美层微调

---

## 1. 这套机制管什么

这套自检不是判断“好不好看”，而是先判断：

- 会不会把同类控件挤成两种样子
- 会不会让某一组切换后突然长滚动
- 会不会把状态角标压成竖排
- 会不会让紧凑工具区又长回大卡堆叠

一句话：

`先卡结构正确，再谈视觉喜好`

---

## 2. 现在的固定入口

在 `frontend-react` 下执行：

```powershell
npm run verify:style-manager
```

这条命令会做两件事：

1. 先执行 `build`
2. 再执行 `scripts/verify-style-manager-contracts.mjs`

---

## 3. 当前已经固化的硬规则

脚本现在会检查这些契约：

- 选项按钮必须是单行紧凑结构，不能再挂说明副文案
- 选项网格必须保持高密度排布，不能退回大卡片
- `细节微调` 必须是双列滑杆布局
- 主题统计区必须保持横向信息带，不回到三张高卡
- 右侧角标必须禁止收缩，避免被正文挤成竖排
- 样式管理主工作区必须保留足够高度预算
- 左侧控制区必须保持独立滚动容器

这些规则主要防“结构回退”。

---

## 4. 每次改完后的人工验收顺序

脚本通过后，再按这个顺序人工过一遍：

1. 切换左侧六个分组
   目标：确认没有哪一组突然出现很长的内滚动

2. 切换右侧四个预览
   目标：确认卡片标题、角标、按钮没有错位或变形

3. 看长文本场景
   目标：确认正文变长时，被压缩的是正文区域，不是角标和状态块

4. 看当前激活态和禁用态
   目标：确认选中项、禁用按钮、主题状态提示都还清楚可辨

---

## 5. 边界说明

这套机制目前优先解决：

- 容易误导用户判断的结构性 bug
- 改一处后把紧凑布局打回原形的问题

它暂时还不负责：

- 审美好不好看
- 配色喜不喜欢
- 不同页面之间更高层的视觉策略

所以以后如果出现“结构没错，但观感一般”，那是下一层设计问题，不是这套自检失效。
