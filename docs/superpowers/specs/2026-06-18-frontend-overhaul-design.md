# 前端整体改造方案

> 日期:2026-06-18
> 状态:已与用户逐节确认,待 writing-plans 转实现计划
> 范围:`frontend-react/` 前端整体改造;后端原则上不动(P1 纯前端,P2/P3 个别小改动另议)

---

## 一、背景与目标

### 1.1 现状痛点

- `App.jsx` 单文件 2732 行 / 120KB,常量、工具函数、prompt 构造、状态管理、整块 JSX 全塞一起,改动越来越痛苦
- `app-shell.css` 57KB 单文件,大量硬编码值,与 `styles.css`(5KB token)和 `styleTheme.js`(940 行运行时主题)三套样式源重叠
- `react-router-dom` 在 `package.json` 里是依赖却没用,`main.jsx` 手写了基于 `pushState` 的极简路由
- `pages/WorkbenchPage.jsx` 是只 import 了一堆东西就没内容的半成品死代码
- 创作台用 3 个 Tab(全书规划/单章设置/正文生成)切换,上下文频繁丢失;作者曾试过左右三分屏但左栏配置区不堪重负
- 章节导航是裸 `<input type="number">`,几十章全靠手输数字
- 样式管理页有 9 维度 + 4 滑块 + 6 预设,维度太碎、预设差异不明显、调完部分组件不跟着变、质感不够舒适

### 1.2 三个目标(都要,分阶段)

1. **可维护性 / 工程化** — 拆分巨型文件、启用标准工具链、清死代码
2. **用户体验 / 交互** — 重组创作台信息架构,理顺"作者写小说的体验"
3. **视觉 / 设计** — 统一视觉语言、重做主题系统、响应式

### 1.3 约束

- 工具处于**小范围内测**,可接受偶尔回归和界面大改,但不能长期不可用
- 因此采用**分阶段渐进改造,每个阶段结束时系统都可用、可上线**
- 后端原则上不动,降低风险

### 1.4 技术栈决策

- **React + react-router-dom**(已装,启用)+ **Tailwind CSS**(新引入,做 utility 样式)+ 少量 headless 组件(如 Radix Primitives 处理弹窗/下拉)
- 仍是手写为主,但基建标准化,长期能控制 CSS 膨胀
- 不用完整 UI 框架(Ant Design / MUI),避免与现有质感深度耦合和样式冲突

## 二、核心洞察:为什么 Tab 和三分屏都不对

项目的数据模型是**两链 × 三层 × 交汇**的工业流水线:

| | 大纲链 | 角色链 |
|---|---|---|
| **全书级**(配一次,月频) | `book_plans` + `novel_outlines`(兼容层) | `novel_characters` + `book_plans.role_summary` |
| **分卷级**(周频) | `storylines.keyBeats` + `volume_timelines` | 剧情线 `characterChangeBoundaries` |
| **章节级**(每章改,高频) | 章节任务表(`chapter_goal`/`key_scenes`/`ending_hook`) | `role_execution`(本章角色怎么演) |
| ↓ **交汇** ↓ | | |
| **正文生成** | 读取 `chapter_plans.structured_content.storyline_context` 快照,受剧情线约束 | |
| **下游** | 校改 → `chapter_feedback` 写回 → 推剧情线 `currentProgress` → 影响下一章 | |

**6 个维度的配置都要进生成,塞进任何恒定高度的左栏都会爆炸**——这就是"Tab vs 三分屏"死结的真正原因。问题不在布局,在于"低频信息和高频信息被强行塞进同一个恒定空间"。

### 2.1 信息架构决策:方案 A — 章节中心 + 抽屉式上下文

三个候选方案的差异在于"用什么机制把低频信息藏起来,又不让作者忘记它们存在":

- 方案 A(采用):常驻双栏(左=本章高频配置,右=正文),低频项做成按需展开的抽屉
- 方案 B(否决):工作流分步向导,5 步串行,适合一次配好从头写,不适合反复跳章
- 方案 C(否决):IDE 式三栏,小屏不可用,本质是把爆炸从左栏转移成全屏占满

### 2.2 抽屉形态决策:形态 1 — 右侧滑入浮层

四种抽屉形态对比后选定:

| 形态 | 看抽屉时能看正文? | 信息容量 | 小屏 | 采用? |
|---|---|---|---|---|
| 1 右侧滑入浮层 | ✗ 遮正文 | 大 | ✓ | **采用** |
| 2 左栏内联手风琴 | ✓ 不遮 | 中(左栏宽限制) | ✓ | 否决(曾试用,左栏变特别长) |
| 3 右侧常驻窄栏 | ✓ 不遮 | 小 | ✗ | 否决(正文被挤压) |
| 4 底部抽屉 | △ 半遮 | 中 | △ | 否决(视觉沉重,切割屏幕) |

**形态 1 被选定的理由**:
- 开发期配置占大头,查上下文主要是为"填对配置",需要"配置+抽屉"同屏,形态 1 正好
- 视觉秩序感最强:从左栏 chip 出发往右栏探出,动线是一条横线,干净
- 保留稳定的左栏锚点,浮层只是叠加,关掉回到完整双栏
- 接近现代设计语言(Notion peek / Linear 详情滑入 / VS Code inline panel)

**交互规则**:
- chip 是小圆角胶囊状标签按钮,放左栏底部,浅色,视觉权重低于主操作
- 点 chip → chip 高亮 → 右栏正文区被滑入浮层覆盖,显示对应内容;左栏配置保持可见
- 同一时间只开一个浮层(点新 chip 自动关旧浮层)
- 再点同一 chip 或点浮层 ✕ → 浮层滑出,chip 恢复普通态

### 2.3 抽屉 vs 资料库:写作视角 vs 编辑视角

抽屉里的"全书信息"不是资料库的复制品,而是"为当前章节过滤过的写作速查":

| 维度 | 资料库(编辑视角) | 创作台抽屉(写作视角) |
|---|---|---|
| 权限 | 完整 CRUD | 只读,想改跳资料库 |
| 范围 | 全部角色/全部设定 | 只显示本章出场相关,其他灰显折叠 |
| 信息 | 全字段 | 一行摘要 + 弧光当前阶段 |
| 重点 | 资料完整可维护 | 写作时一眼抓到的关键约束 |

四个低频 chip 的写作视角呈现:
- 📖 全书设定 → 抽屉只显示平台/题材/核心矛盾一句话
- 🗺 剧情线 → 抽屉只显示本章命中的 beat + 前后 beat + 本章伏笔操作
- 👤 角色档案 → 抽屉只显示本章出场角色摘要 + 弧光当前阶段
- 📚 分卷 → 抽屉只显示当前卷主题 + 本章在卷中位置

## 三、四阶段路线图

| 阶段 | 主题 | 目标 | 产出后系统状态 |
|---|---|---|---|
| **P0 地基** | 工程化基建 | 启用 react-router、引入 Tailwind、拆分 App.jsx、清死代码 | 视觉和功能完全不变,但代码可维护;后续改造有干净地基 |
| **P1 骨架** | 创作台信息架构重构 | 落地方案 A:章节中心双栏 + 右侧滑入抽屉;章节导航条;hero 区改作者视角 | 创作台换新布局,功能不变但交互更顺,旧 Tab 退场 |
| **P2 肌肉** | 组件化与交互打磨 | 各区域抽成独立组件;补章节列表导航、生成进度、快捷键;L2 功能收进次级入口 | 创作台完整且顺手,单文件不超过 400 行 |
| **P3 皮肤** | 视觉统一与设计系统 | Tailwind 结构 token + 重做主题系统(4 预设 + 明暗);统一组件视觉;响应式 | 视觉统一专业,CSS 可控 |

**关键原则**:
- P0 不改任何视觉和功能——只搬代码、启工具链,是安全网,保证改造期间随时可回退
- 每个阶段独立可交付,P0 完了能上线,P1 完了也能上线,不依赖后续阶段
- 优先级:地基(P0)→ 骨架(P1,解决最痛的信息架构)→ 肌肉(P2)→ 皮肤(P3)。视觉放最后,因为视觉建立在不稳定结构上会反复返工

## 四、P0 地基阶段

核心约束:**不改视觉、不改功能**,只搬代码和启工具链。

### 4.1 启用 react-router-dom(替换手写路由)

现状 `main.jsx` 手写 6 条路由。改造换 `createBrowserRouter` / `RouterProvider`,路由表集中管理。现有路由一一对应迁移:`/`、`/books`、`/books/outlines`、`/books/characters`、`/books/chapters`、`/changelog`、`/start-guide`、`/generation-logic`、`/style-manager`、`/workbench`。`/books/*` 子路径用嵌套路由收编。

### 4.2 引入 Tailwind CSS

引入 Tailwind,但 **P0 阶段不替换现有 CSS**——只装好、配好、能编译。现有 `app-shell.css` 和 `styles.css` 原样保留继续生效。从 P1 开始才逐步用 Tailwind 写新组件,旧 CSS 在 P3 统一清理。P0 风险最低。

### 4.3 拆分 App.jsx(2732 行 → 按职责分文件)

按"纯函数 / hook / 组件"三层拆:

```
src/
├─ lib/
│  ├─ constants.js        # GENRE_LABELS / PLATFORM_LABELS / ROLE_* 等枚举
│  ├─ chapterPlan.js      # composeStructuredOutline / normalizeRoleExecution / withStructuredChapterPlan 等纯函数
│  └─ revisionDiff.js     # buildRevisionDiff / similarityScore 等校改 diff 纯函数
├─ hooks/
│  └─ useWorkbench.js     # 创作台状态+逻辑(useState + 生成/校改/反馈处理函数)
├─ components/workbench/
│  ├─ WorkflowTabs.jsx
│  ├─ PanelCard.jsx
│  ├─ Modal.jsx
│  └─ ...
└─ App.jsx                # 只剩路由页面组装 + 调用 useWorkbench,目标 < 300 行
```

拆分顺序:先搬纯函数(零风险)→ 再搬 hook(需验证状态流)→ 最后拆组件。每步拆完都能跑、视觉不变。死代码 `pages/WorkbenchPage.jsx` 直接删。

### 4.4 P0 验收标准

- `npm run dev` 能跑,所有路由可访问
- 创作台所有功能行为与改造前完全一致
- 单文件最大不超过 500 行(App.jsx 目标 < 300)
- Tailwind 已配置但未强制使用,现有 CSS 原样生效
- `react-router-dom` 真正接管路由,手写路由代码删除

## 五、P1 骨架阶段 — 创作台新信息架构

在 P0 干净地基上,把创作台从"3 个 Tab 单列堆叠"重组成"方案 A:章节中心双栏 + 右侧滑入抽屉"。

### 5.1 新布局结构

```
┌─────────────────────────────────────────────────────────────┐
│ 顶部全局条(常驻,窄)                                          │
│ 📖书名 | 第N章 章名 | 主线标签        ◂上章 ‹N/总› 下章▸    │
├──────────────────────────┬──────────────────────────────────┤
│ 左栏:本章配置(常驻)      │ 右栏:正文工作区(常驻)          │
│ ┌──────────────────────┐ │ ┌──────────────────────────────┐ │
│ │ 📝 本章任务          │ │ │   正文预览/编辑(始终可见)  │ │
│ │  目标/场景/冲突/钩子 │ │ │                              │ │
│ ├──────────────────────┤ │ ├──────────────────────────────┤ │
│ │ 🎭 本章角色执行      │ │ │ ▶生成  ✎校改  ⚙参数         │ │
│ ├──────────────────────┤ │ ├──────────────────────────────┤ │
│ │ 🚫 约束/禁止项       │ │ │ 💬 反馈摘要/下一章重点       │ │
│ ├──────────────────────┤ │ └──────────────────────────────┘ │
│ │ ⬆ 上一章反馈承接     │ │                                  │
│ └──────────────────────┘ │                                  │
│ [📖全书][🗺剧情线][👤角色][📚分卷]  ← chips,点开右侧滑入浮层 │
└──────────────────────────┴──────────────────────────────────┘
```

关键设计点:
1. **顶部全局条**替代 hero 区("React Workbench Prototype"开发期文案退场)。只放:书名、当前章号章名、主线标签、章节前后导航
2. **左栏**只保留 4 块章节级高频项:本章任务、角色执行、约束、上章反馈(排序经用户确认)
3. **右栏**常驻,永远可见。上半正文,下半操作按钮+反馈。正文不再被 Tab 藏
4. **低频 chips**放左栏底部。点 chip → 右侧滑入浮层(形态1),遮右栏正文,左栏配置保持可见
5. **3 个旧 Tab 退场**。全书规划移到 `/books` 资料库页(全书级数据不该占创作台),单章设置和正文生成合并进新双栏

### 5.2 章节导航改进

顶部全局条放 `‹ 第N/总 ›` 前后翻章按钮 + 可点击展开的**完整章节列表**,每章三态标记:有正文(实心点)/仅有计划(空心点)/空章(灰点)。点列表项直接跳章。

数据来源:`/books/:id/chapters` + `/books/:id/chapter-plans` 列表接口(都已存在),前端合并两个列表算状态。**纯前端,后端不动。**

### 5.3 全书规划区处理

创作台 Tab1(全书规划:书籍操作/信息/角色/分卷概览)是全书级只读展示,不是每章要改的。P1 把这块从创作台移到 `/books` 资料库详情页。创作台顶部全局条"📖书名"可点击跳资料库详情。全书信息同时以低频 chip 形式留抽屉(写作视角摘要)。

### 5.4 后端配合

**P1 是纯前端改造,后端完全不动。** 四个抽屉要的数据全在现有接口返回里:
- 📖 全书设定 → 现有 `planningState`
- 🗺 剧情线 → `allStorylines` + `plan.target_storylines`(前端镜像精简版 beat 命中逻辑做展示)
- 👤 角色档案 → `/books/:id/characters`(已存在,加进 bundle)
- 📚 分卷 → `volumePlans`(已拉)

唯一可选项(非阻塞):后端 beat 命中逻辑 `buildChapterStorylineContext` 在 `routes/ai.js` 里只有生成时跑。抽屉展示用前端精简版(按 `chapterApprox` 匹配)即可,后续 P2/P3 可考虑加 `GET /books/:id/chapter-plans/:n/storyline-context` 接口统一,但不阻塞 P1。

### 5.5 P1 验收标准

- 创作台呈现新双栏布局,3 个旧 Tab 消失
- 左栏 4 块高频配置 + 底部 4 个低频 chips,全部可读写,数据与后端正确同步
- 点任意低频 chip → 右侧滑入浮层显示对应内容(写作视角),点 ✕ 关闭
- 顶部全局条:书名/章号/主线/前后翻章/章节列表(三态),全部可用
- 正文生成、校改、反馈写回三条链路行为与改造前一致
- 全书规划内容在 `/books` 详情页可查看,创作台抽屉有写作视角摘要

## 六、P2 肌肉阶段 — 组件化与交互打磨

P1 落地骨架,P2 拆可视组件 + 补交互。目标:**单文件不超过 400 行,每个组件职责单一**。

### 6.1 组件拆分

```
src/components/workbench/
├─ GlobalBar.jsx          # 顶部全局条
├─ ChapterConfigPanel.jsx # 左栏:本章任务/角色执行/约束/上章反馈
├─ ContentWorkspace.jsx   # 右栏:正文预览/生成按钮/反馈
├─ ContextDrawer.jsx      # 右侧滑入浮层容器(管理开合/方向/当前 chip)
├─ drawers/
│  ├─ BookSettingDrawer.jsx
│  ├─ StorylineDrawer.jsx
│  ├─ CharacterDrawer.jsx
│  └─ VolumeDrawer.jsx
├─ ChapterList.jsx        # 章节列表(三态标记)
├─ RevisionEditor.jsx     # 校改编辑器(从 App.jsx 抽出)
└─ GenerationBanner.jsx   # 生成状态/风险简报
```

每个组件接收 props 数据 + 回调,不直接调 API(API 调用集中在 `useWorkbench` hook)。

### 6.2 功能分层:多而不乱的原则

功能多 ≠ 效率低,冲突在于"功能都堆在主路径"。解法是三层入口:

| 层 | 位置 | 原则 |
|---|---|---|
| **L1 主路径** | 右栏按钮/左栏配置/顶部条 | 每章都用,一键触达 |
| **L2 次级** | "⚙参数"折叠/"更多"下拉 | 偶尔用,多一步但不挡路 |
| **L3 抽屉/设置** | 低频 chips/独立页 | 很少用,不占主区 |

**关键洞察**:现在生成参数(字数/温度/爽点)裸露在主区,是 L2 功能占了 L1 位置。P2 收进折叠区后,主路径按钮反而比现在少,功能却更多。

P2 范围 = L1 打磨 + L2 五项:
- 生成参数(字数/温度/爽点标签)→ 收进"⚙参数"折叠
- 连续性审计结果(空降风险)展示 — 后端已有 `auditGeneratedContent`
- 正文版本对比(本次 vs 上次)
- 伏笔台账速查 — 后端有 foreshadowing 接口,进剧情线抽屉
- 导出 TXT — 后端有 `/books/:id/export`,放全局条"更多"

L3 留后续(独立页):批量章节生成、剧情线/卷时间线生成、多书管理、成本/token 统计。

### 6.3 补齐的交互

1. **章节列表三态** — 完整列表,有正文/仅有计划/空章三态,点跳章
2. **生成进度反馈** — 加计时 + 完成提示,避免干等
3. **快捷键** — `Ctrl+Enter` 生成、`Esc` 关抽屉、`[`/`]` 前后翻章
4. **抽屉记忆** — 同一书同一章重开时恢复上次打开的抽屉(localStorage)
5. **未保存提示** — 左栏配置改了没保存就翻章/生成,弹确认

### 6.4 P2 验收标准

- 创作台所有可视区域都是独立组件,`App.jsx` 只做组装
- 单文件最大 400 行
- 章节列表三态导航可用
- 生成有计时反馈,快捷键可用
- 校改编辑器独立成组件,功能与改造前一致
- L2 五项全部落地,生成参数已收进折叠区

## 七、P3 皮肤阶段 — 视觉统一与设计系统

P3 最后收口视觉。放在最后,因为视觉建立在不稳定结构上会反复返工——P0/P1/P2 把结构和组件稳定后,P3 才有干净着力点。

### 7.1 双轨 token:结构不变量 + 氛围变量

用户意图是"一个设计结构基准 + 用户自定义氛围风格"。现有样式管理页(9 维度 + 4 滑块 + 6 预设)实现得不好,推倒重做。

**双轨设计**:
- **结构不变量 = Tailwind token**(写死,用户不可调):间距阶梯 4/8/12/16/24、圆角档位、字号比例、控件高度(`--btn-height` 40px 等)。保证不浮夸、不崩坏、组件尺寸天生一致
- **氛围变量 = 主题系统**(用户可选):预设切换背景/品牌色/文字色等氛围

**为什么这样能满足"有个性又舒适"**:个性来自预设间的强烈差异,舒适来自每个预设内部打磨到位——不让用户自己组合 9 个维度赌能凑好看。

### 7.2 主题系统重做:4 预设 + 明暗

砍掉所有碎维度(密度/控件缩放/间距缩放/圆角选择/面板质感选择/导航风格/操作风格),只留两项:

```
样式管理
─────────────────────────────
氛围:  [纸页] [冷光] [深幕] [信号]    ← 4 选 1(分段控件)
明暗:  ○浅  ●深                       ← 2 选 1
─────────────────────────────
        [实时预览区]
─────────────────────────────
```

四个预设,每个一个明确性格:
- **纸页·暖书桌** — 米黄底 + 琥珀橙,像旧书桌写稿,温暖有纸张感(参考 iA Writer 暖色)
- **冷光·工作台** — 冷灰底 + 石墨蓝,干净克制信息密度高(参考 Linear / Notion 浅色)
- **深幕·夜行** — 深灰底 + 钴蓝点缀,护眼专注强对比(参考 VS Code 深色 / Raycast)
- **信号·霓虹边** — 浅紫底 + 电紫点缀,有个性略张扬(参考 Framer / Raycast 彩色)

**为什么砍掉控制项**:之前痛苦链是"组件尺寸乱 → 加控制项 → 控制项太碎 → 调了也不满意"。新方案从源头斩断第一环(组件尺寸统一走 token),后面整条链都不需要。用户不再需要"调尺寸"的能力。

### 7.3 组件视觉语言统一

| 元素 | 规范 |
|---|---|
| 卡片(PanelCard) | 统一圆角 12px、边框、阴影、内边距 |
| 按钮 | 实心(主操作)/ 描边(次操作)/ 文字(三级)三态,统一高度 40px |
| chip | 浅色胶囊,激活态品牌色填充 |
| 输入框 | 统一边框/聚焦态/高度 |
| 状态色 | 成功/警告/错误三色 |
| 间距 | 4/8/12/16/24/32 阶梯,不硬编码 |

### 7.4 响应式

- 桌面 ≥1200px:双栏 + 抽屉,完整布局
- 平板 768-1199px:双栏变窄,抽屉变全屏浮层
- 手机 <768px:单栏堆叠,左栏配置和右栏正文上下排,抽屉全屏

鉴于这是创作工具,手机端只保证"不崩溃能查看",不追求"手机上高效创作"——创作以桌面为主。

- 统一中英文混排间距、字体栈

### 7.6 P3 验收标准

- 样式管理页只有"氛围 4 选 1 + 明暗 2 选 1",无碎维度
- 三档断点(桌面/平板/手机)均可用

## 八、风险与回退

- **P0 是安全网**:只搬代码不改视觉功能,任何后续阶段出问题都可回退到 P0 状态

- **后端稳定**:P1 纯前端,后端不动,出问题范围可控;P2/P3 个别小后端改动另议且非阻塞
- **数据兼容**:所有阶段不改数据库结构,不动后端接口契约,现有数据全程可用
